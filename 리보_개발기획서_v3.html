    이번 개정에서 확정된 세 가지

    2026-08-06 확정 기획안 대비 바뀐 것만 먼저 적는다. 나머지 절은 이 세 결정을 전제로 쓰였다.

    변경 01 · 트리거 무조작 단일 → 이중 모드 기본은 그대로 무조작 자동 감지. 손을 쓸 수 있는 사용자(초기 ALS, 후두암 수술 직후, 일시적 발성 상실)를 위해 수동 ON/OFF 세션을 옵션으로 추가한다. 절대 제약은 유지된다 — 수동 모드는 선택지이지 전제가 아니다.
    변경 02 · 스택 상주 GPU → GPU 없이 관리형 API 웹·API·인증·DB·스토리지는 Vercel + Supabase. GPU는 직접 붙이지 않는다 — TTS와 음성 클로닝은 관리형 API(ElevenLabs)로 분리한다. 원가가 고정비에서 변동비로 바뀌고, 고정 문장 캐시 덕에 초기 원가는 오히려 낮다(§12).
    변경 03 · 범위 고정 15문장 + 자유 문장 베타 1차는 고정 문장으로 출시하되, 자유 문장 추론을 Stage 3 공개 베타까지 올리는 것을 로드맵에 명시한다. 다만 자유 문장은 §14의 악용 방어를 무너뜨리므로 별도 설계가 선행되어야 한다.
    유지되는 절대 제약
    사용자는 손을 쓰지 않아도 쓸 수 있어야 한다. ALS는 진행되면 손을 못 쓰고 뇌졸중은 편마비가 흔하다. 버튼을 필수로 만드는 순간 대상자의 상당수가 배제된다. 수동 모드를 추가하되, 수동 모드 없이도 온보딩부터 일상 사용까지 전 경로가 완결되어야 한다. 이 조건을 깨는 기능은 어떤 이유로도 머지하지 않는다.
    이번 스택 결정의 요지
    GPU를 우리가 운영하지 않는다. 오픈 웨이트 TTS 모델은 좋지만 돌리려면 GPU 서버가 필요하고, 그게 이번에 떼기로 한 바로 그 고정비다. ElevenLabs로 시작하면 GPU 없이 클로닝까지 되고, 서버리스와 궁합도 좋다. 자체 호스팅은 볼륨이 충분히 커진 뒤의 원가 최적화 옵션으로 로드맵에 남긴다(§6.2 · §12.1).
    02

    제품 정의와 경계

    무엇을 하는 물건인지, 그리고 결정적으로 — 무엇을 하지 않는 물건인지. 뒤쪽이 의료기기 규제와 직결된다.

    하는 것

    • 카메라 앞에서 소리 없이 입모양을 만들면, 등록된 문장 중 하나로 인식해 텍스트로 화면에 띄우고 음성으로 출력한다.
    • 출력 목소리는 기본 프리셋 · 동성 가족 · 본인 옛 음성 중 선택하며, 언제든 교체 가능한 프로필이다. 클로닝은 첫 출시부터 제공한다.
    • 얼굴 영상은 단말을 벗어나지 않는다. 서버로 가는 것은 발화 구간의 입술 좌표뿐이다.

    하지 않는 것 — 규제 경계

    하지 않음이유결과
    진단 · 치료 · 예후 판정디지털의료제품법상 의료기기 정의의 핵심은 “질병을 예방·관리 또는 치료하기 위한 목적”이다사용 목적을 “보완대체 의사소통(AAC)”으로 고정. 마케팅 문구에서 “치료·개선·호전” 금지
    임상적 효과 표방효능 표방은 의료기기 광고 규제 대상“의사소통 보조”, “발화 대체”로만 기술
    임의 텍스트 입력Stage 1~2에서 합성 가능한 문장은 등록된 것뿐보이스피싱 악용이 기능이 아니라 구조로 차단됨(§14)
    얼굴 영상 서버 저장생체정보 원본 보관은 파기 의무·유출 리스크를 동시에 짊어진다“개인정보 부담이 낮다”가 정책이 아니라 아키텍처가 됨

    AAC 소프트웨어가 의료기기가 아니라고 명시한 식약처 공식 유권해석·사례는 이번 조사에서 확인하지 못했다. 위 경계는 정의 조문 해석에 근거한 설계 방침이며, 출시 전 식약처 사전 상담 또는 비의료기기 확인 신청이 필요하다(§11).

    대상 환자군과 규모

    가장 큰 유입뇌졸중연 63만 명 규모. 갑자기 온다 → 사전 녹음이 거의 없다. 목소리를 필수 입력으로 받으면 이 군이 온보딩에서 통째로 막힌다. §6의 “목소리는 관문이 아니다” 원칙이 여기서 나온다.
    가장 절실한 유입ALS · 운동신경질환최대 95%가 발성을 잃는다. 진행성이므로 보이스뱅킹 수요가 명확하고, 동시에 손 기능도 잃으므로 무조작 트리거가 필수인 군이다.
    가장 빠른 검증후두 절제 · 기관절개인지·운동 기능은 유지된 채 발성만 잃는다. 입모양은 정상이므로 인식 정확도 검증에 가장 적합한 초기 파일럿 집단.

    환자군 규모 수치는 기존 신청서에 기재된 값을 그대로 옮긴 것이며 이 문서에서 별도로 재확인하지 않았다.

    03

    사용자 흐름

    로그인 → 캘리브레이션 → 일상 사용. 각 단계에서 손을 몇 번 써야 하는지를 함께 적는다.

    3.1 계정 구조 — 누가 로그인하는가

    설계 함정
    손을 못 쓰는 사람은 구글 로그인을 스스로 할 수 없다. 인증 흐름을 환자 본인에게 맡기면 절대 제약이 온보딩 단계에서 곧바로 깨진다. 따라서 계정 소유자와 서비스 대상자를 분리한다.
    역할실체권한
    계정(account)보호자 · 간병인 · 또는 본인. Google OAuth로 인증되는 단위Supabase auth.users결제, 프로필 관리, 동의 제출, 문장 편집
    대상자 프로필(subject)실제로 말하는 사람. 계정 1개에 프로필 N개(요양기관 대비)자체 테이블 subjects캘리브레이션 데이터, 음성 프로필, 발화 로그의 귀속 단위
    런타임 세션병상 옆 태블릿에 영구 로그인 상태로 고정재로그인 없이 곧바로 발화. 세션 갱신은 백그라운드에서 자동

    구글 로그인 단독으로 가는 이유 — 비밀번호 재입력이 없고, 고령 보호자도 이미 안드로이드 기기에서 로그인되어 있을 확률이 높다. 리스크는 구글 계정이 없는 보호자이며, Stage 2에서 카카오 로그인 추가를 검토한다(국내 고령층 커버리지).

    3.2 온보딩 — 최초 1회

    1. 구글 로그인 — Supabase Auth. 손 사용 1회(보호자).
    2. 동의 수집 — 생체정보 처리 별도 동의, 음성 사용 동의, 대상자가 의사표현 불가한 경우 법정대리인 동의. 동의 주체가 계층마다 다르다(§11.4). 손 사용 수 회(보호자).
    3. 카메라 권한 + 조명 체크 — 얼굴 인식 성공 여부를 실시간 피드백으로 보여준다. 여기서 각도·거치 위치가 결정되고, 이후 정확도의 상당 부분이 여기서 갈린다.
    4. 캘리브레이션 녹화 — 화면이 문장을 하나씩 띄우고 대상자가 소리 없이 따라 한다. 손 사용 0회: 다음 문장으로의 진행은 발화 구간 검출로 자동 전환된다.
    5. 목소리 선택 — 성별·연령대 프리셋으로 즉시 시작. 가족 음성이나 본인 옛 음성은 나중에 올려도 된다(§6).
    6. 첫 발화 테스트 — 대상자가 아무 등록 문장이나 말해보고, 나온 소리를 함께 듣는다. 이 순간이 온보딩 완료 지점이다.

    04

    트리거 — 이중 모드 설계

    “언제부터 입모양을 인식할 것인가”에 대한 답. 기본은 아무것도 누르지 않는 쪽이다.

    4.1 모드 A · 무조작 자동 (기본값)

    별도의 트리거 장치를 만들지 않는다. 대신 분류기 자신이 “이건 말이 아니다”를 판단하게 한다.

    NONE 클래스. 15문장만 학습한 분류기는 씹는 동작을 줘도 “화장실”이라고 답한다 — 반드시 하나를 골라야 하기 때문이다. 학습 데이터에 씹기·하품·기침·웃기·무성 잡담을 NONE 클래스로 넣으면 16클래스 문제가 되고, 트리거 장치가 불필요해진다.

    판정 게이트 · 4단

    NONE조용히 폐기아무 일도 일어나지 않는다. 로그에도 남기지 않는다.
    < 0.70조용히 폐기저확신. 사용자는 자기가 뭘 잘못했는지 알 필요가 없다.
    0.70 – 0.90화면에 문장만 표시 · 소리 없음반복하면 확정된다. 이것이 손을 쓰지 않는 취소 수단이다 — 알아듣지 못하면 다시 말하는 건 원래 하던 행동이라 배울 게 없다.
    ≥ 0.90즉시 합성 · 발화문장 텍스트를 캐시 또는 TTS API로 넘긴다.
    임계값을 보수적으로 잡는 이유는 두 오류의 비용이 비대칭이기 때문이다. “말했는데 안 나옴”은 다시 말하면 되지만, “말 안 했는데 나옴”은 사고다. 그래서 검증 게이트에 자연 상태 10분 오발화 0회를 정확도와 나란히 놓는다.

    05

    시스템 아키텍처 — Vercel + Supabase + ElevenLabs

    “버튼을 누르면 계속 입모양을 인식해야 하는데, 그 인식을 서버리스에서 할 수 있나? 그리고 GPU도 없이 TTS가 되나?” 이 절이 그 두 질문에 답한다.

    핵심 답
    인식 루프는 서버리스에서 돌리지 않는다. 돌릴 필요도 없다. 서버리스 함수는 “요청 하나에 응답 하나”이고 상태를 유지하지 않는다. 30fps로 흘러드는 프레임을 계속 지켜보는 일은 사용자 브라우저의 클라이언트 컴포넌트가 맡는다. 서버로 가는 것은 이미 잘려 나온 발화 구간 하나이고, 그건 완벽한 단발성 함수 호출이다. 합성용 GPU도 우리가 갖지 않는다 — 문장 텍스트를 ElevenLabs API로 넘기면 오디오가 돌아온다. 즉 “계속 인식”은 클라이언트의 일, 서버리스는 “구간 하나를 문장 하나로 바꾸는” 일, 합성은 관리형 API의 일이다.

    5.2 각 조각이 왜 거기에 있는가

    결정근거
    구간 검출은 브라우저입이 멈춰 있는 대부분의 시간 동안 좌표를 서버로 보낼 이유가 없다. 대역폭·원가·프라이버시 모두 여기서 결정된다.
    정규화는 서버브라우저 JS와 서버 Python에 각각 구현하면 미세한 불일치로 정확도가 조용히 무너진다. 학습에 쓴 코드와 추론에 쓰는 코드가 같은 파일이어야 한다.
    판정 게이트는 서버클라이언트 코드는 신뢰할 수 없다. 임계값을 클라이언트가 정하면 “말 안 했는데 나옴”의 책임 소재가 사라진다.
    합성은 관리형 APIGPU를 직접 운영하지 않기 위해서다. ElevenLabs가 상시 워밍·클로닝·스트리밍을 대신 해주므로 콜드스타트가 없고, 우리는 쓴 만큼만 낸다. 고정 문장은 결과를 캐시해 재호출 자체를 없앤다(§12).
    Node Runtime, Edge 아님Edge Runtime은 응답 시작을 25초 내로 요구하고 Node API가 제한된다. TTS API 호출 대기와 오디오 스트리밍은 Node Runtime + Fluid Compute 쪽이 맞는다.
    Fluid ComputeI/O 대기(= 외부 TTS API 응답 대기) 중에는 Active CPU 과금이 멈춘다. TTS 호출을 기다리는 이 서비스의 패턴과 정확히 맞물린다.
    WebSocket을 쓰지 않음Vercel WebSocket은 Public Beta이고 연결이 단일 인스턴스에 고정되며 브로드캐스트가 안 된다. 발화당 단발 HTTP 요청이면 충분하므로 지속 연결 자체가 불필요하다.

    06

    목소리 파이프라인

    사용자가 이전 음성 파일을 넣으면 그걸 기반으로, 안 넣으면 기본 목소리로. 그 “안 넣으면”이 대다수라는 것이 설계의 출발점이다.

    목소리를 관문으로 두지 않는다. 뇌졸중은 갑자기 오기 때문에 사전 녹음이 거의 없는데, 대상 환자군 중 규모가 가장 크다. 목소리를 필수 입력으로 받으면 가장 큰 환자군이 온보딩에서 막힌다. 목소리 확보는 사용의 전제가 아니라 진행 중인 과정이다.

    6.1 세 경로 · 하나의 API

    1일차 · 즉시기본 프리셋성별·연령대 프리셋 목소리로 목소리가 없어도 시작한다. ElevenLabs에 프리셋 voice를 미리 만들어 두면 그 자체가 기성 음성 라이브러리가 된다.
    며칠 뒤동성 가족 목소리아들 → 아버지. 성대 구조가 닮아 프리셋보다 훨씬 가깝다. 제공한 가족 본인의 별도 동의가 필요하다.
    찾는 대로본인 옛 음성영상·통화 녹음·음성메시지·보이스뱅킹. ElevenLabs Instant Voice Cloning은 짧은 녹음으로도 되므로 “쓸 만한 녹음”의 기준이 낮다(길수록 정확 · §15 W3).

    세 경로 모두 같은 API에 등록된 voice만 다르다. 런타임 합성이므로 프로필을 바꾸면 다음 발화부터 바뀐다 — 같은 문장이 다른 목소리로 나온다. 바뀐 프로필의 고정 문장은 백그라운드에서 다시 합성해 캐시를 갱신한다.

    6.2 합성 엔진 — 지금은 API 하나, 자체 호스팅은 나중

    지금은 관리형 API 하나로 프리셋·가족·본인 세 경로를 모두 처리한다. 자체 모델 호스팅은 GPU가 필요하므로 이번 범위에서 뺀다.

    6.3 참조 음성 처리 규칙

    • 업로드 → 비공개 버킷. Supabase Storage private bucket + RLS. 접근은 짧은 만료의 signed URL로만.
    • 전처리는 서버에서 1회. 무음 제거·노이즈 감소·라우드니스 정규화 후 클립을 정리해 ElevenLabs에 voice로 등록한다.
    • voice_id만 보관. 발화마다 참조 음성을 다시 올리지 않는다. 프로필 생성 시 ElevenLabs가 돌려주는 voice_id만 저장하고, 원본 오디오는 등록·클립 추출 후 파기하거나 사용자 요청 시 즉시 파기한다.
    • 합성 결과 캐시. (문장 × voice_id) 조합의 오디오를 Supabase Storage/CDN에 저장해 재사용한다. 같은 문장·같은 목소리는 다시 합성하지 않는다 — 원가와 지연을 동시에 없앤다(§5.3 · §12).
    • 목소리는 민감정보로 취급. 음성은 화자 식별 목적일 때 생체인식정보로 분류될 가능성이 높다. 별도 동의 · 분리 보관 · 파기 절차를 처음부터 붙인다(§11.2).

    문장 세트 — 최소로 추리는 방법

    “이걸 최적화해서 어느 정도 다 할 수 있는 문장들을 최소한으로 추릴 수 있지 않을까?” — 가능하다. 다만 최적화 목적함수가 하나가 아니라 셋이다.

    7.1 서로 반대로 당기는 두 힘

    힘 1 · 의미 피복적은 문장으로 많은 상황을문장을 추상적·다목적으로 만들수록 적은 수로 넓은 상황을 덮는다. “불편해요” 하나가 여러 상황을 삼킨다.
    힘 2 · 시각적 변별입모양이 서로 달라야분류기는 소리가 아니라 입모양만 본다. 의미가 아무리 유용해도 다른 문장과 입모양이 겹치면 못 쓴다. 이것이 일반적인 AAC 코어 어휘 연구를 그대로 가져다 쓸 수 없는 이유다.
    실제로 걸리는 함정
    “물 주세요 / 약 주세요 / 도와주세요” — 세 문장이 “주세요”라는 동일한 어미를 공유한다. 전체 길이의 60% 이상이 동일한 입모양이고, 판별에 쓸 수 있는 정보가 앞 1~2음절에 몰린다. 게다가 “물(ㅁ, 양순 폐쇄)”과 “약(ㅇ, 개방)”은 구분되지만 “물”과 “뭐”는 거의 같다. 문장 목록은 의미로 고르고 끝나는 게 아니라, 고른 뒤 입모양 거리로 한 번 더 걸러야 한다.

    7.2 선별 절차

    1. 후보 풀 구성 — 기존 AAC 코어 어휘 연구 + 간병 현장 관찰 + 병원에서 쓰는 의사소통 그림판 문구. 목표 50~80개.
    2. 긴급도 우선 고정 — 응급 문장은 빈도가 낮아도 무조건 포함한다. 빈도 기반 최적화가 제일 먼저 버리는 것이 “숨이 안 쉬어져요”이기 때문이다. 이건 최적화 대상이 아니라 제약 조건이다.
    3. 비제메(viseme) 시퀀스로 인코딩 — 각 문장을 입모양 단위 열로 바꾼다. 한국어 양순음(ㅁㅂㅍ)·원순모음(ㅗㅜ)·개구도가 주된 축이다.
    4. 쌍별 거리 계산 — DTW 등으로 후보쌍 거리를 구하고, 거리가 임계 이하인 쌍은 한쪽을 동의어로 교체한다(“약 주세요” → “약이요”).
    5. max-min 분산 최적화 — 남은 후보에서 K개를 뽑되 쌍별 최소거리를 최대화한다. 이것이 “최소한으로 추리기”의 수학적 형태다.
    6. 파일럿 혼동행렬로 교정 — 실제 녹화 데이터로 학습해 혼동행렬을 뽑고, 상호 혼동률이 임계 이상인 쌍을 병합하거나 교체한다. 여기서만 진실이 나온다.

    8.2 격리와 보관

    RLS모든 테이블에 예외 없이표준 패턴은 auth.uid() 기반. 대상자 데이터는 subjects.account_id를 거쳐 검증한다 —
    using (exists (select 1 from accounts a where a.id = subjects.account_id and a.user_id = auth.uid())). Storage의 storage.objects에도 동일 정책을 건다.
    보관 · 파기원본은 특징 추출 후 지체없이얼굴 영상은 애초에 서버에 오지 않는다. 참조 음성 원본은 voice 등록·클립 추출 후 파기하거나 사용자 요청 시 즉시 파기. 좌표 시퀀스는 보유 기간을 명시하고 계정 삭제 시 연쇄 파기. 민감정보는 다른 개인정보와 분리 보관한다.

    8.3 학습 데이터의 2차 이용 — 지금은 못 한다

    타임라인 주의
    수집한 좌표 데이터를 다른 사용자를 위한 공통 모델 학습에 쓰는 것은 “수집 목적 외 이용”이다. 개인정보 보호법 개정(2026-09-08 공포)이 익명·가명처리가 곤란한 정보(음성·이미지 등)에 대해 목적 외 이용 특례를 신설했지만 시행은 2027-03-09다. 2026년 현재는 적용할 수 없다.

    12.1 왜 이제 변동비인가

    지금 · 관리형 TTS API (채택)고정비 바닥 0 + 캐시로 한계원가 0ElevenLabs 같은 관리형 API는 제공자가 수많은 고객으로 상시 워밍을 유지하므로 콜드스타트가 없고, 우리는 쓴 만큼만 낸다. 게다가 고정 문장은 (문장 × 목소리)를 한 번만 합성해 캐시하므로 반복 발화의 한계원가가 0이다. 사용자가 적어도 비싸지지 않는다.
    나중 · 자체 GPU 호스팅월 $350+ 고정 · 볼륨 임계 후오픈 웨이트 모델(§6.2)을 L4급 GPU에 상시 올리면 한계원가는 0에 가깝지만 사용자 0명이어도 월 $350이 나간다. API 변동비가 이 고정비를 넘어서는 대량 구간에서만 유리하다. 캐시 때문에 그 교차점은 멀다.
    서버리스 GPU(건당 과금·자체 호스팅)는 콜드스타트 4–6초라 응급 제품에 못 쓴다 — “아파요” 하고 5초 뒤에 소리가 나는 건 제품이 아니다. 그래서 자체 호스팅은 오직 ‘상시 워밍’만 후보이고, 그건 곧 고정비다. 관리형 API는 이 딜레마 자체를 없앤다: 콜드스타트도 없고 고정비 바닥도 없다.

    결과적으로 방향이 뒤집혔다. 예전 GPU 설계에서는 초기 소수 사용자 구간이 구조적으로 가장 비쌌지만, 관리형 API + 캐시 구조에서는 초기 원가가 가장 낮다. 대량 구간에 이르러 API 변동비가 자체 GPU 고정비를 넘어서면, 그때 §6.2 오픈 웨이트로 전환해 원가를 다시 낮춘다.

    ① 상업 이용 가능한 데이터로 처음부터 학습(자체 수집 + AI Hub 상업 계약 협의), ② LRS 라이선스 보유자와 상업 라이선스 협의, ③ 음소 단위 자체 분류기 + 한국어 언어모델 디코딩으로 우회. 세 경로 모두 데이터 확보가 병목이며, ③이 가장 현실적이다. 자유 문장의 비용은 모델이 아니라 데이터다.
